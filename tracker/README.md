# tracker/ — the template's own roadmap tracker

Three ticket families live here. **`F01`–`F14`** are the post-0.6 release foci — one ticket
per focus, `epic: roadmap`. **Release-prefixed follow-ups** (`070-*`, `080-*`, `090-*`,
`0911-*`, …) are small, independently schedulable items filed at a release's close or
review, `epic: follow-up`; the prefix names the release that surfaced them, not the
release that fixes them. **`B<n>-*`** are decisions
from the maintainers' design reviews held while training new operators, `epic: roadmap`;
`B1` is the first review, `B2` the next, and so on. Those reviews' working notes are not
public, so every `B<n>` ticket opens with an `## Origin` section that states the decision
in full. A reader needs nothing outside this repository to act on it. A decision that
needs no work in this repository gets no ticket; it is recorded on the ticket or ADR it
affects.

This is a plain root-level folder, **not** a materialized `inspire_kb/` — the template repo
is not a governed project, and a root `inspire_kb/` here could confuse the upgrade
fingerprinting. The format still mirrors the on-disk contract a governed project gets from
`inspire-task` (`tracker-format.md`) — one file per ticket, same frontmatter schema,
`Open | Done | Cancelled`, closed tickets move to `tickets/archive/` — with two declared
deviations:

- **Descriptive ids.** Files and `id:` use the focus key (`F01-derive` … `F14-semantic-types`) or the
  release-plus-slug form (`070-glossary-population`) instead of random `TASK-xxxxxx`.
  Random ids exist for concurrent creation in live projects; a roadmap with stable natural
  keys reads better by name.
- **Extended `skills:` enum.** Tickets may name `extract`, `lesson` and `spike`; the shipped enum
  predates those skills.

## Three rules for filing

Adopted 2026-08-19, after 0.7.0 closed four foci and left seven follow-ups behind. The
concern was a ratchet: follow-ups are generated by every release review and scheduled by
nothing, so the count can only climb. These rules attack the generation rate, not the
backlog.

**1 — File a ticket only for pending work that does not fit elsewhere.** If the work
belongs to an open focus's surface, it is an amendment to that focus, not a new ticket.
Fit means *surface*, never chronology: bundling something into a release merely because
it is residue from the previous one is not routing, it is stacking. Applied on adoption
day, this absorbed `070-scanner-count` into F08 (which ships the fifth scanner brief that
falsifies the count) and `070-prose-style-nits` into F04 (whose pre-work already opens
`prose-style.sh` to split it).

**2 — A null-urgency ticket is not a ticket.** A "nice to have" with no defect behind it
loses every scheduling contest it enters; its only durable effect is to make the queue
longer and less trustworthy to read. Record the idea where the work would happen and let
it go. `070-claudemd-skills-shape` was cancelled on adoption day under this rule, by its
own words: "zero urgency… nothing about it is broken today".

**3 — A ticket is standalone.** The only hard relationship is `blocked_by`; `related_to`
is informational and carries no scheduling meaning. There is deliberately no way to say
"A must be answered by the time B ships" — and wanting to say it is the signal that **A is
a subtask of B, not a ticket.** Fold it in under rule 1 instead of inventing a dependency
the tracker does not have. If A genuinely stands alone, it needs no peg: it carries an
importance and competes for a window like everything else.

The corollary is about *done conditions*, and it belongs inside the ticket rather than
between tickets. A ticket whose answer might be "the current behavior is fine" must say
so in its own acceptance criteria, so that ratifying the status quo closes it **Done with
zero code changed**. Without that, the only way to close is to build something, and the
cheap correct answer never gets picked — which is what makes a question look like it needs
an external deadline when what it actually needed was an honest done condition.

**One ticket, one theme.** A ticket that needs the word "and" in its own summary is two
tickets, and a ticket nobody can pick up as a next task is a bag. `070-carryforwards` was
cancelled on 2026-08-19 for exactly that: nine unrelated bullets, invisible to anyone
scanning the open set. It is archived with a table routing every bullet to the ticket
whose theme it shares — a cancelled bag stays readable, so the routing is never lost.

`blocked_by` carries **hard** dependencies only; soft ordering preferences live in
`related_to` plus a note in the body. A `blocked_by` entry is cleared when the blocker
closes, and the ticket's Notes say so — the archive keeps the history, the open set keeps
only what is still true.

**Factory work goes to the Factory's tracker.** The INSPIRE Factory
(Genomcore/inspire-factory) runs emanation, builds the code and reads the KB with its own
deriver. A ticket here covers what the KB says and what attended sessions do. When a
change here needs matching work in the Factory (a format the Factory's deriver must read,
a rule its agents must follow), the ticket says so in a note, and the Factory ticket is
filed in the Factory's tracker when the change here lands, never before.
