# ADR — The upgrade path: shipped manifests as the content baseline, replayable layout hops

- **Status:** Accepted — 2026-08-04 (shipped in 0.4.0)
- **Closes:** [[adr-runtime-lifecycle-and-lessons]] gap **3** — *"No changelog or
  migration path"* — in its **migration-path half only**. That ADR's **D6** (update as
  a rebuild that re-derives lessons onto the new base) and **D7** (the changelog as a
  release artifact) are untouched and still the target; nothing here re-decides them.
- **Builds on:** [[adr-plugin-delivery]] **D1–D2** (the plugin is the delivery vehicle;
  the runtime is materialized into the project and lives in git). Upholds its **D4d**
  (`base/bin/test/` never materializes) and **D4e** (the KB is `inspire_kb/`, visible).
- **Scope:** How an operator at any released version reaches the installed plugin's
  version. Deterministic mechanics only — file identity, layout moves, and the
  decision of whose copy of a file wins. Not the semantic re-derivation of lessons.

---

## Context

An operator with INSPIRE at `M.m.p` had no supported route to `M'.m'.p'`.
`/inspire:update` handled exactly one case — same layout, newer payload — and
hard-refused anything older than 0.3, printing six manual steps instead.

Two problems had to be solved together, because they need different amounts of
judgement and the wrong split makes both unsolvable:

1. **Layout moves between versions.** `.inspire_kb/` → `inspire_kb/`, `.claude/bin/` →
   `.inspire/bin/`, `.claude/hooks/` → `.claude/inspire/hooks/`. Fully deterministic,
   and must be replayable version by version so a 0.1 install and a 0.3 install reach
   the same place by different-length routes.
2. **The operator edited files INSPIRE owns.** This needs a decision per file, and
   getting it wrong either destroys their work or silently pins them at stale content
   while the version string claims otherwise.

The second problem is the hard one, and it was previously unsolvable for a reason worth
stating plainly: **answering it requires knowing what INSPIRE shipped at the operator's
version, and that information did not exist anywhere trustworthy.** Without it, an
upgrade can see only "disk differs from what I am about to install" — which is the same
observation for a file the operator carefully customized and a file that is merely
three releases old. The only safe response to that ambiguity is to prompt about
everything, which is not an upgrade path; it is a questionnaire.

## Decisions

Decision numbers are scoped to this ADR. A reference to another ADR's decision is
always qualified.

### D1 — Per-version hash manifests, shipped in the plugin, are the content baseline

`plugin/manifests/<version>.json` records `{version, released, commit, layout, files}`,
where `files` maps every **project-relative materialized path** that version shipped to
its `sha256`. One manifest per release, generated from that release's own tree, committed
to this repo, and distributed with the plugin.

This is the datum that makes everything else possible. It is not a second opinion about
what shipped — it is the only record of it.

Manifests are generated by `plugin/scripts/gen-manifest.sh`, which reads content through
read-only git. Two eras are handled by one generator, because the materialized path set
differs: `pre-0.3` (`install.sh` copied `.inspire/{skills,bin,hooks}` →
`.claude/{skills,bin,hooks}` wholesale, fixtures included — which is why a 0.2 project
legitimately owns 192 files) and `0.3` (`base/{bin,hooks,skills}` → `.inspire/bin`,
`.claude/inspire/hooks`, `.claude/skills`, minus what does not ship).

**What ships is defined exactly once.** `_base_excluded` in `lib/merge.sh` is the single
definition, asked by the classifier, the applier *and* the generator. A second copy of
that rule is the only place it can drift, and a manifest disagreeing with the applier
about what ships turns every affected path into a phantom creation or a phantom deletion.

### D2 — `.inspire.lock` is provenance only, and carries no `files` map

The lock records `inspire_version`, `released`, `template_sha`, `installed_at`. Nothing
else. It is a **version hint**, never load-bearing.

Three reasons, and the first alone is sufficient:

1. **It lives on the operator's machine**, where it can be edited, and the pre-0.3
   update path rebaselined skipped files to their *drifted* hash — so its record of
   "what we shipped" could already have been overwritten with "what you changed it to."
2. **It is frequently absent.** All three pre-0.3 installers wrote it only
   `if [ -f "$MANIFEST" ] && command -v jq` — so a pre-0.3 project may have no lock at
   all, and per-file history existed on disk for exactly two releases.
3. **Two disagreeing answers to "what did we ship?" are worse than one.** Per-file
   hashes live in the shipped manifests, where the operator cannot edit them, and
   nowhere else.

`template_sha` stops being the dead literal `"unknown"` and carries the release commit,
which `inspire-lesson` stamps onto every lesson.

### D3 — Detection fingerprints the project against every manifest, and refuses rather than guesses

The source version is established by hashing the project and scoring it against every
shipped manifest, not by reading the lock. This handles a missing lock, a hand-edited
lock, and the historical case where **0.1.0 named two different runtimes** (`2fa511b`
vs `d41fd89` both shipped `version: 0.1.0`; only the former is tagged).

Below a floor of matched paths, or on an unresolved tie between manifests with different
content, detection **fails and reports** instead of picking. Never-downgrade is enforced
here, in code, by a pure-bash `version_cmp` — not by `sort -V`, whose `-V` support is not
dependable across the BSD/GNU split and which now gates a destructive operation rather
than a PR.

### D4 — Layout verification asserts structure, never content

Before replaying anything, the detected version's **layout signature** is asserted:
which containers and roots must and must not exist. Structure only.

This is a decision, not an omission. An operator who edited a skill, deleted a validator,
or removed a whole skill directory **is using INSPIRE correctly** — the runtime is
materialized into their project precisely so it can diverge. None of that may block an
upgrade, so content is never a precondition for one.

### D5 — Layout hops are executable scripts, one per version that moved something

`plugin/scripts/hops/<version>.sh` is bash that performs the move. It is not data an
agent interprets, and not prose an agent follows.

The reasoning is a matter of where the determinism lives. A layout change is exactly the
part of an upgrade with no judgement in it; expressing it as instructions for a model to
carry out converts a tested, deterministic operation into a non-deterministic one, and
buys nothing. `layouts.tsv` declares each layout's structural markers; each hop script
declares its literal operations; nothing is derived at runtime.

**A hop's absence is the no-op.** There is no registry to keep in sync — a version that
moved nothing has no file, so the chain runner cannot disagree with reality about which
versions matter. 0.3.1 moved nothing and therefore has nothing.

Hops perform five operations (`hop_mv`, `hop_rm`, `hop_rm_owned`, `hop_unregister_hook`,
`hop_report`) and **never rewrite file contents**. Rewriting an operator's prose or source
code is riskier than leaving a stale path reference in it; see Consequences.

### D6 — Three hashes per path decide every file; only a genuine conflict asks

For each path: **A** = what the manifest says we shipped at the operator's version,
**B** = what is on disk, **C** = what is about to be installed.

| A | B | C | outcome |
|---|---|---|---|
| = | = | ≠ | untouched but stale → **take ours, silently** |
| ≠ | — | = C | already edited into the new content → **no-op** |
| ≠ | — | = A | edited, upstream unchanged → **keep theirs, silently** |
| ≠ | — | ≠ both | both sides changed, differently → **ask** |
| absent | — | exists | new upstream file → **create** |
| exists | = A | absent | upstream dropped it → **delete** |
| exists | ≠ A | absent | edited a file we are removing → **ask** |
| **absent** | **exists** | **absent** | **never ours → keep, by construction** |

The last row is the one that matters most and costs the least. A file INSPIRE never
shipped — an operator's own stack profile inside a skill directory we own — is kept
because it never enters the decision set, not because a special case rescues it. This
replaces `rm -rf "$dest" && cp -R`, which destroyed exactly those files, and it is why
the guarantee holds for files nobody has thought of yet.

**INSPIRE deletes only what it can prove it shipped**, per path, against the manifest —
never inferred from location. Folder-wide operations are acceptable only where every byte
inside is provably ours; otherwise the operation is per file. Erring toward caution here
costs a slower loop and nothing else.

### D7 — Classification runs before the hops, and reduces to a set of hashes

Manifests for a pre-0.3 version record pre-0.3 paths, and those paths stop existing the
moment the hops move them. So classification runs first, in source-space, and its output
is reduced to a keep-set of **content hashes** — which are invariant under `mv`. The
applier then runs after the hops, driven by the target layout.

The alternative — remapping every path forward through every hop in the chain — makes
each decision depend on the correctness of the whole chain, for no gain. Moving a file
does not change its bytes; that is the whole trick.

### D8 — Act-or-record is one implementation with a terminal switch

Every operation either performs itself or records what it would have done, decided at
one point inside the operation rather than by the caller. `--mode plan` is the same code
path as `--mode update` with the switch flipped, and **writes nothing at all** — not the
report file, not the lock, not one byte.

This replaces roughly eleven independent `DRY_RUN` checks scattered through
`materialize.sh`. Each was a place where the plan could disagree with the act, and one
already did: an act/record divergence over symlinked paths said `keep` in one mode and
`delete` in the other. A plan that can drift from the act it predicts is worse than no
plan, because it is trusted.

### D9 — The report is part of the system, and is held to the same standard as the code

The upgrade's contract with the operator has three invariants:

1. Nothing of the operator's is destroyed.
2. Nothing is left silently stale while the version claims otherwise.
3. **The report never claims something that did not happen.**

The third has teeth because it was violated, destructively. A hop report described
`.inspire/bin/` as retired residue and suggested removing it, while the same hop moved
fourteen validators *into* that directory — at 0.3+ it is the live destination. A blind
verification of a skill-driven 0.1→0.4 upgrade found the runtime gone: the hop had done
its job correctly, then the agent read the report and did what it said.

Two rules follow, and they are enforced in review rather than by a test:

- A hop report **states facts**. It never names a live path as residue, and it uses no
  imperative verbs about disposal. What to do with a genuinely dead path is the
  operator's call; naming the path is the whole obligation.
- The journal records what **happened**, never what was intended. Journal-after-mutation,
  never journal-then-hope — an earlier version logged deletions that never occurred,
  which is invariant 3 inverted.

The uncomfortable lesson is that every test invoked `materialize.sh` directly. The prose
was the only untested component in the system, and it was the component that caused the
damage.

### D10 — The KB is additive in both init and update

`inspire_kb/` is product content INSPIRE never owns. Missing skeleton files are added; a
path already on disk is **never** replaced, in either mode. There is no delete outcome
for the KB at all.

### D11 — Git is read-only against the operator's repository

No `git mv`, `git rm`, `git add`, commit, push, or worktree creation, ever. Tracking and
ignore state are read — via `git ls-files` / `check-ignore --no-index` — only where they
change what gets **reported**, never what gets done, and never to emit a command premised
on an assumed configuration. The operator's `.gitignore` is the operator's.

## Alternatives considered and rejected

**Trust `.inspire.lock`'s `files` map as the baseline.** Rejected per D2. It was in fact
implemented and then removed: the map existed for two releases and had to go, because the
mechanism cannot ask the operator's machine what the operator's machine is supposed to be
compared against.

**Express hops as declarative data, or as prose for an agent to interpret.** Rejected per
D5 — it moves the one genuinely deterministic part of the upgrade into a
non-deterministic executor. (The one place prose *did* end up load-bearing produced the
D9 incident.)

**Textual three-way merge of skill prose.** Rejected. Skills are natural language, not
code: a line-wise merge of two edits can produce a skill that reads fine and means
something neither side intended. Whole-file outcomes only, and a true conflict is escalated
rather than resolved.

**Derive the moved set from a directory listing.** Rejected. `mv .claude/bin .inspire/bin`
drags the operator's own scripts along. The moved set is enumerated literally, per file.

**A rename table for renamed skills.** Rejected as unnecessary. `inspire-learn` →
`inspire-lesson` falls out of D6 as a delete plus a create, with the old directory pruned
when its last owned file leaves. A rename table would be a second, weaker description of
something the hash sets already describe exactly.

**Regenerate the release manifest from its tag before opening the PR.** Rejected as
circular — the tag is cut when the PR merges, so the manifest for the release being
prepared is generated from the commit carrying the version bump. The release guard
therefore compares everything **except** the `commit` field: that field necessarily names
the commit before the manifest's own, so comparing it would demand a regeneration whose
own commit invalidates it, forever.

## Consequences

**Good.**

- One command upgrades from any released version, including pre-0.3, which is no longer a
  refusal but simply the longest chain.
- Prompts collapse from "every file this release touched" to "files both sides changed,
  differently." In a real 0.1→0.4 upgrade of a used project, that was one file.
- Files the operator added inside directories INSPIRE owns now survive, by construction.
- `--mode plan` is a trustworthy preview, because it is the same code.
- `template_sha` is real, so lesson provenance points at an actual commit.

**Accepted costs.**

- **A file resolved in the operator's favour diverges from the release manifest
  permanently**, and will fail any future manifest-conformance check on that path. This
  is the correct trade — the alternative is destroying their edit — but it means manifest
  conformance is a diagnostic, not a health check.
- **Stale path references survive in file contents.** The KB root rename moves the
  directory and rewrites nothing, so an operator's prose, tickets and source code may
  still name `.inspire_kb/`. Per D5 this is deliberate; it is also not yet reported, which
  is a real gap (see Staging).
- **INSPIRE-authored KB scaffolding is never refreshed.** Layer READMEs live under
  `inspire_kb/`, so D10 makes them the operator's, so they keep their install-era text
  and can end up documenting a convention the current runtime contradicts. Refreshing
  them would mean deciding that some KB files are ours after all, which reopens D10.
- **Symlinks are not supported** anywhere in a managed path. Nothing INSPIRE ships is one.
  A declared limitation, not a gap to close.
- **Pre-0.3 staging directories are retained wholesale.** `.inspire/{skills,templates}`
  and `.inspire/bin/test/` may hold operator edits that were never re-installed, and the
  0.2.1 manifest lists no `.inspire/**` paths at all, so per-file ownership is not
  provable there. Reported and left, per D6's caution rule.
- **Six test suites, no CI.** The two upgrade suites take minutes because they build
  period-correct fixtures, and `test-upgrade.sh` is not parallel-safe.

**A trap worth recording,** because it silently cost this repo seven assertions: a pre-0.3
project legitimately *retains* `.inspire/{bin,hooks,skills,templates}` as the staged source
`install.sh` copied FROM. Any assertion of the form "the destination exists" therefore
passes whether or not the code under test ran. Assert the source side too, or choose a path
the old installer cannot have staged.

## Staging

Built here: detect · verify · hops · reconcile, the manifests and their generator, the
release guard that blocks a PR whose manifest does not describe its tree.

Not built, and deliberately out of scope:

- **Lesson re-derivation** — `adr-runtime-lifecycle-and-lessons` D6's four outcomes and
  D7's changelog. This ADR delivers the deterministic half; that is the semantic half.
- **Reporting residual old-root references.** The upgrade will not rewrite file contents
  (D5), but it should say which files still name a path it moved. Currently it says nothing,
  which is invariant 2 applied to content rather than files.
- **A signal when a KB layer is superseded.** `98_skill_learnings/` survives beside
  `98_lessons/` and the `inspire-lesson` skill reads only the latter, so pre-existing
  lessons become invisible to the skill meant to consult them. Nothing is lost and moving
  them is the operator's call under D10 — but they currently get no signal at all.
